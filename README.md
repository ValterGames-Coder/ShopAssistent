# ShopAssistent — Telegram-бот с RAG

Docker-версия тестового задания: Python 3.12, aiogram, Ollama, PostgreSQL 17 и
pgvector. Модели работают локально, платный API не нужен. Для этой версии не нужны
Python и Ollama на хосте: все компоненты запускает Docker Compose.

## Запуск

Нужны Docker Engine/Desktop с запущенным движком, Linux containers и Compose v2.24+.
Для первого запуска потребуется скачать образы и примерно 3,1 ГБ моделей.
Ориентир по памяти — 8 ГБ для Docker; скорость CPU-инференса зависит от компьютера.

```sh
git clone https://github.com/ValterGames-Coder/ShopAssistent.git
cd ShopAssistent
cp .env.example .env
```

В PowerShell вместо последней команды: `Copy-Item .env.example .env`.
Заполните `TELEGRAM_BOT_TOKEN` токеном своего бота из [BotFather](https://t.me/BotFather).
При необходимости измените `POSTGRES_PASSWORD` до первого старта БД.

```sh
docker compose up -d --build bot
docker compose logs -f models index bot
```

Compose дождётся готовности БД и Ollama, скачает `qwen3:4b` и `embeddinggemma`,
построит индекс из шести документов, затем запустит Telegram long polling.
Появление `Run polling for bot` в логах означает подключение к Telegram.
Откройте своего бота и отправьте `/start`. Токен передаётся только контейнеру `bot`.

**Один токен — один процесс polling.** Если этот же бот работает в локальной
версии проекта, остановите тот процесс перед запуском Docker-копии или используйте
другого бота. Эта копия не останавливает локальную версию автоматически.

База и модели хранятся в volumes. Порты наружу не публикуются; нужны только
исходящие подключения для загрузки моделей и к Telegram. Остановка с сохранением данных:

```sh
docker compose down
```

Не добавляйте `-v`, если хотите сохранить БД, модели и отчёты.

## NVIDIA GPU

Основной Compose работает на CPU. При настроенной поддержке NVIDIA в Docker:

```sh
docker compose -f compose.yaml -f compose.gpu.yaml up -d --build bot
```

Для дальнейших команд с GPU используйте те же два `-f`. Конфигурация GPU необязательна.

## Прокси

Если прямое соединение с Telegram недоступно, заполните `TELEGRAM_PROXY_URL`.
Для прокси на Windows/macOS-хосте пример: `http://host.docker.internal:7890`.
`127.0.0.1` внутри контейнера указывает на сам контейнер. Прокси должен разрешать
подключение из Docker; для Linux настройте доступный контейнеру адрес самостоятельно.
Пример не включает чужие адреса или учётные данные. Прокси применяется только к Telegram.

## Как устроена защита

1. Вопрос превращается в embedding через Ollama.
2. pgvector находит релевантные пункты регламента по косинусному сходству.
3. Связанные правила возврата подаются вместе с исключением о браке.
4. LLM возвращает JSON: источники, тип вопроса и наличие недостающих сведений.
5. Сервер проверяет источники и срок возврата, затем собирает текст из базы знаний.

Свободный текст модели не отправляется пользователю. Она не может добавить новую
цену, дату, скидку или статус. Для явных запросов о конкретном заказе предусмотрен
отказ до LLM: базы заказов нет. Общие условия доставки не становятся обещанием
доставки заказа №1842. Пользовательское сообщение не обновляет регламент.

Системный промпт реально читается из `SYSTEM_PROMPT.md`; база — `knowledge.json`.
Индекс содержит отпечаток регламента и embedding-модели, устаревший индекс не
используется. Замена индекса проходит одной транзакцией. Для шести документов
достаточно точного поиска; приблизительный HNSW-индекс не требуется.

RAG и JSON Schema не гарантируют идеальную интерпретацию каждого вопроса:
модель может выбрать существующий, но нерелевантный факт или излишне отказать.
Семантическое качество проверяется живым прогоном. Вычисления сроков по календарным
датам не реализованы; поддержаны числа дней и некоторые словесные формы.

Команды: `/start`, `/help`, `/sources`. Бот принимает текст в личных сообщениях.
Каждый вопрос независим; история и данные клиентов не сохраняются. Логи содержат
статус, ID источников, время и класс ошибки, без токенов и текстов переписки.

## Проверки

Unit-тесты, без токена, моделей и работающей БД:

```sh
docker compose --profile test run --rm --build tests
```

Проверки реального PostgreSQL/pgvector в отдельной временной БД:

```sh
docker compose --profile test run --rm --build integration-tests
docker compose --profile test stop test-db
```

Тесты проверяют ранжирование, порог, смену версии/размерности и откат неудачного
импорта. Они создают отдельную схему с уникальным именем и не меняют данные бота.
В `docs/github-actions-check.yml.example` приложен готовый CI-шаблон: unit-тесты,
проверки БД, валидация Compose и сборка образа. Он не запускается автоматически.
Для включения перенесите его в `.github/workflows/check.yml` через GitHub или
с учётными данными, имеющими право создавать workflows.

Живой прогон трёх вопросов без Telegram-токена:

```sh
docker compose --profile tools run --rm --build eval
```

Ответы печатаются в консоль и сохраняются в Docker volume `reports`.
Код завершения 1 означает, что один из критериев не пройден.
Чтобы получить файл на хосте, можно оставить контейнер после прогона:

```sh
docker compose --profile tools run --name shop-assistant-eval eval
docker cp shop-assistant-eval:/app/reports/crash-test.json ./reports/crash-test.json
docker rm shop-assistant-eval
```

Каталог `reports` есть в репозитории. Экспорт не зависит от прав на bind mount
в Linux. Если имя контейнера уже занято, используйте другое имя или удалите
предыдущий завершённый контейнер с этим именем.

Произвольный вопрос через тот же конвейер:

```sh
docker compose run --rm index python app.py ask "Сколько стоят X1?"
```

## Изменение регламента или моделей

Обновите `knowledge.json`, сохраняя шесть ID и согласованность `max_days` с текстом,
либо измените модели в `.env`. Затем:

```sh
docker compose stop bot
docker compose build
docker compose run --rm models
docker compose run --rm index
docker compose up -d bot
```

Chat-модель должна поддерживать JSON Schema и `think=false`. После смены моделей
повторите живой краш-тест. Изменение `POSTGRES_PASSWORD` не меняет пароль в ранее
созданном PostgreSQL volume автоматически.

## Материалы для сдачи

- `knowledge.json`: шесть пунктов регламента.
- `SYSTEM_PROMPT.md`: используемый системный промпт.
- `CRASH_TEST.md`: условия проверки и ссылка на исходный живой прогон.
- `docs/crash-test-local-reference.json`: реальный прогон исходной локальной версии
  на SQLite. Он явно помечен как SQLite и не является подтверждением запуска Docker.
- `reports/crash-test.json`: ваш новый результат после Docker-прогона.

Токен, `.env`, модели, базы, журналы и локальные инструменты в репозиторий не входят.
